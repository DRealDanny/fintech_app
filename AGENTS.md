# Fintech App Development Standards & Architecture Guidelines

This repository follows **Clean Architecture (Feature-First)** and strictly adheres to **SOLID Principles**. All code written for this project must follow the patterns, conventions, and technology choices outlined below.

## 2. Clean Architecture Layer Separation (Feature-First)

Every feature in `lib/features/<feature_name>/` must be partitioned into three distinct layers:

```text
lib/
├── core/                                # Shared infrastructure across features
│   ├── constants/                       # Colors, dimensions, typography, endpoints
│   ├── errors/                          # Failure models & Exception handlers
│   ├── network/                         # Dio client, interceptors, SSL pinning
│   ├── storage/                         # Secure storage wrapper & Hive initialization
│   ├── theme/                           # Light and dark theme palettes
│   └── utils/                           # Formatters (currency, masks), validators
│
└── features/
    └── <feature_name>/                  # e.g., auth, onboarding, wallet, transfer
        ├── data/
        │   ├── datasources/             # Remote (Retrofit API) & Local (Hive/SecureStorage)
        │   ├── models/                  # DTOs with Freezed & fromJson/toJson
        │   └── repositories/            # Repository implementations (implements domain interfaces)
        │
        ├── domain/
        │   ├── entities/                # Pure Dart business objects
        │   ├── repositories/            # Abstract repository contracts (interfaces)
        │   └── usecases/                # Single-purpose business actions
        │
        └── presentation/
            ├── controllers/             # Riverpod Notifiers / StateNotifier / Providers
            ├── screens/                 # AutoRoute page widgets
            └── widgets/                 # Reusable UI components specific to this feature
```

## 3. Layer Responsibilities & Rules

### A. Domain Layer (Pure Business Logic)
* **Zero Flutter Imports**: Contains only pure Dart code. No `package:flutter/...`, no `BuildContext`, and no UI elements.
* **Entities**: Core business objects representing fintech concepts (e.g., `UserAccount`, `Transaction`, `Wallet`).
* **Repository Interfaces**: Abstract contracts defining operations without caring *where* the data comes from (network, cache, memory).
* **Use Cases**: Each use case performs exactly one task (e.g., `TransferFundsUseCase`, `GetAccountBalanceUseCase`).
* **Error Handling**: Use cases and repository contracts must return `Future<Either<Failure, SuccessType>>` using `fpdart`. Never throw untyped exceptions across layer boundaries.

### B. Data Layer (Data Retrieval & Persistence)
* **Data Transfer Objects (DTOs / Models)**: Extend or map to domain entities. Use `freezed` and `json_serializable` to parse raw JSON from Retrofit and serialize to Hive.
* **Data Sources**:
  * **Remote**: Typed REST interfaces generated by `@RestApi()` from `retrofit` with `dio`.
  * **Local**: Fast key-value and object persistence via `hive`, or sensitive token storage via `flutter_secure_storage`.
* **Repository Implementations**: Implement the contracts declared in the Domain layer. Orchestrate calling remote and local data sources, handling network drops, caching policies, and transforming exceptions into domain `Failure` types.

### C. Presentation Layer (UI & State)
* **Riverpod Providers**: State is exposed via `Notifier` or `AsyncNotifier` (from `riverpod_annotation`). Notifiers call domain use cases and emit immutable UI state.
* **Immutable UI States**: Model screen states using Freezed unions (e.g., `AsyncValue<T>` or `State.initial()`, `State.loading()`, `State.data()`, `State.error()`).
* **Auto Route**: Every screen must be registered as an `@RoutePage()`. Navigation must be triggered through `AutoRouter.of(context)` or auto-generated route extensions, keeping UI decoupled.
* **Zero Direct API Calls**: Screens and widgets must NEVER call repositories or HTTP clients directly; they interact exclusively with Riverpod controllers/notifiers.

## 4. SOLID Principles Implementation Guide

1. **S — Single Responsibility Principle (SRP)**:
   - A widget only displays UI.
   - A Riverpod notifier only manages presentation state.
   - A use case only executes one business process.
   - A repository only handles data retrieval and caching orchestration.

2. **O — Open/Closed Principle (OCP)**:
   - Extend functionality via polymorphism, interfaces, and composable widgets rather than modifying existing tested code.

3. **L — Liskov Substitution Principle (LSP)**:
   - Repository implementations and mock data sources must be completely swappable with their domain interface contracts without breaking behavior.

4. **I — Interface Segregation Principle (ISP)**:
   - Keep repository and data source interfaces lean. Avoid monolithic interfaces like `ApiRepository` with 50 methods; split them by domain concern (`AuthRepository`, `WalletRepository`, `TransferRepository`).

5. **D — Dependency Inversion Principle (DIP)**:
   - High-level domain logic must never depend on low-level data layer implementations (Dio, Hive, SQLite).
   - Both must depend on abstractions (domain repository interfaces).
   - Riverpod providers serve as the Dependency Injection mechanism binding abstractions to implementations.

## 5. Security & Fintech Specific Rules

* **Sensitive Data Isolation**: Never store plaintext passwords, credit card PINs, CVVs, or session tokens in `Hive` or `shared_preferences`. All sensitive authentication tokens (JWTs, refresh tokens, encryption keys) **must** be stored in `FlutterSecureStorage`.
* **Floating-Point Currency Ban**: Never use `double` for sensitive money balances or transaction amounts to prevent precision loss. Use integer cents/kobo or dedicated fixed-point arithmetic (`Decimal`), and format via `intl` `NumberFormat`.
* **Dio Network Configuration**:
  - Always attach auth tokens via Dio `Interceptors`.
  - Include token refresh interceptor logic to handle 401 Unauthorized responses seamlessly.
  - Enforce timeout bounds (e.g., connectTimeout: 10s, receiveTimeout: 15s).
* **Biometric Lock**: Protect app resume states using `local_auth` to require Face ID / Fingerprint / Passcode when returning from background.

## 8. Android Emulator & Windowed Mode Rules (`mobile-mcp`)

1. **NEVER Run Headless:** Never launch the Android emulator with `-no-window` or headless flags. The user must be able to see the visible emulator window at all times.
2. **Check Before Launching:** 
   - First, run `mobile_list_available_devices`. 
   - If `emulator-5554` is already online, attach to it directly—do NOT start a new instance.
3. **How to Launch If Offline (Windowed Mode Only):**
   - If no emulator is running, launch it visibly with a standalone GUI window using PowerShell:
     ```powershell
     Start-Process "$env:LOCALAPPDATA\Android\Sdk\emulator\emulator.exe" -ArgumentList "-avd Medium_Phone_API_37.0"
     ```
   - Wait for `emulator-5554` to come online, then launch the app onto it (`flutter run -d emulator-5554`).

## 9. Android Emulator Verification Workflow (Mobile MCP)

Always verify your work directly inside the running Android Emulator using `mobile-mcp`:

1. **Connect to Emulator:** Call `mobile_list_available_devices` to lock onto the active Android emulator.
2. **Hot Reload Changes:** After editing Dart code, trigger a hot reload (or run `adb shell` / terminal reload) so the emulator reflects your latest code.
3. **Visual & Structural Check:**
   - Call `mobile_take_screenshot` to visually inspect the live Android screen for layout alignment, styling, and RenderFlex overflow stripes.
   - Call `mobile_list_elements_on_screen` to inspect interactive widgets and get their exact screen coordinates.
4. **Interactive Testing:** Use `mobile_click_on_screen_at_coordinates`, `mobile_swipe_on_screen`, and `mobile_type_keys` to walk through the user flow on the emulator and confirm nothing crashes.
